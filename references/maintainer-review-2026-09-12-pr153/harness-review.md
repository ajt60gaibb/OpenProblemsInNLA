## Completed architecture checks

- **Binding to committed inputs:** `snapshot` copies ordinary tracked HEAD blobs into a fresh directory, excludes untracked build products, rejects symlinks/submodules and committed `.lake` or compiled artifacts, requires the selected project to be clean, and records hashes. Input hashes are checked after preparation and comparison. This establishes the run's source identity; it does not automatically establish that a statement was previously reviewed or matches an informal problem.
- **Statement/proof separation:** Comparator builds and exports Challenge first, retaining its export in the parent process before building Solution. Writable Solution build access is limited to the fresh project's `.lake`; subsequent modification cannot rewrite the retained Challenge string. Selected theorem names, universe parameters, and types must match exactly. The defining constants reachable through their types must match structurally and transitively; definition holes are forbidden by this harness. A selected Solution declaration must actually be a theorem.
- **Axioms and kernel replay:** the checker follows proof as well as type dependencies, including opaque bodies, inductives, constructors and recursors, and rejects every reachable axiom outside the configured subset of `propext`, `Quot.sound`, and `Classical.choice`. It parses exported declarations as data, creates an empty Lean environment, and calls the real replay API. Quotient declarations are regenerated by Lean and compared with the exported originals afterward. Harness success requires exit zero and both final markers, so the earlier kernel-success print cannot mask a quotient post-check failure.
- **Pins:** project dependencies must be immutable 40-hex HTTPS GitHub git revisions, with contained `.lake/packages`; floating and path dependencies are rejected. Project/tool toolchains must match Lean 4.33.1. Bootstrap verifies locked sources, builds the tools, and records binary hashes; later use validates sources, binaries, environment receipt and version. This relies on the separately trusted host/toolchain/tool directory.
- **Controls inspected:** actual raw-kernel honest/invalid-proof/counterfeit-quotient cases; theorem-kind/type and custom-axiom Comparator cases; extra `sorry` and native-decision axiom rejections; build/export write confinement, network and AF_UNIX denial, process namespaces, no host-process signaling, capabilities, nested-wrapper resistance, and adapter argument rejection. CI adaptations preserve the probe assertions and add explicit deadlines and execution of the nested-wrapper attempt. These are meaningful controls, not a completeness proof.

## Trust boundary and disclosure

The strict adapter uses Bubblewrap with a read-only host root, separate namespaces, dropped capabilities, and at most the selected `.lake` writable bind; Landrun adds restrictions, while the outer systemd service prohibits AF_UNIX. Its Linux/non-root prerequisites fail closed on this macOS host.

Host-file confidentiality is **not** provided: candidate code can read host-readable files and emit them to logs. Root's current worktree clarification in `tools/lean/HARNESS.md:71–77` accurately states that limitation and requires an isolated credential-free runner. Challenge and its imports, Lake configuration/build graph, dependency/cache preparation, infrastructure and toolchain are separately trusted. The unsandboxed `lake env true` / optional `lake exe cache get` preparation is inside that declared boundary; a trusted build graph must not cause candidate Solution execution there. The harness does not mechanically attest this semantic property of an arbitrary trusted Lake configuration.

## Addendum: native-primitive question resolved by independent source tracing

**Updated disposition: PASS for this bounded harness source review under its documented trust model.** The original unresolved conclusion above is retained as review history. This addendum supersedes that reservation; it does not certify the final integrated PR or claim a runtime experiment.

I independently read the decisive Lean 4.33.1 functions identified by the other reviewer, at revision `819816b2e0a3bf405af45ae5c7af2491d8f5bee6`:

1. `Environment.lean:1530–1544` creates a fresh environment with no modules and initial extensions. `CompilerM.lean:83–118` initializes the IR map empty; `findInterpDecl` at lines 145–154 looks only in the current environment's module/local IR. Replayed logical declarations do not constitute IR declarations.
2. `Replay.lean:58–101,176–189` adds the exported declarations with `Kernel.Environment.addDeclCore`; it does not compile or import executable code. Conversion back to an elaborator environment (`Environment.lean:642–646`) preserves that kernel environment rather than attaching the executable's imported module environment.
3. `ir_interpreter.cpp:1157–1171` routes kernel reduction through that converted environment. `call_boxed` at lines 1065–1071 calls `lookup_symbol` **before** the nullary-constant/global-value loading path. All initial lookup paths—including process-global native-symbol-cache hits at lines 835 and 843—call `get_decl`; lines 872–877 throw when the environment has no IR declaration. Interpreter-local caches are specific to the environment (`with_interpreter`, lines 429–442), so a previously imported environment cannot supply a cached IR declaration here.

Consequently, the proposed counterfeit name cannot obtain a native result during this fresh replay. If the kernel attempts that reduction, IR lookup fails before native execution. If no such reduction is needed, the ordinary declaration/proof kernel checks remain applicable. No inconsistent native reduction follows from the omitted primitive names in this implementation. This resolves the exact question that withheld my earlier approval; it is not a general completeness proof for every kernel primitive.
